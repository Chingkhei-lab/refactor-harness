# v0.3 corrected: the stage-2 mutation result, re-measured

This document corrects `docs/results/harness-20261120.md` and the v0.3 release.
It does not move the tag: `v0.3` stays at `603f90a`, marked superseded, and
`v0.3.1` carries this.

Everything below is from the corrected code, re-run. The numbers that changed are
quoted with the number they replace, because a report that only shows the new
value hides the reason it exists.

## 1. What was wrong

`v0.3` reported stage-2 mutation as **100 of 100 mutants killed by both oracles**.
That number measured the mutator, not the harness:

`apply_site` serialised the whole module with `ast.unparse(tree)` after changing
one node. Every mutant therefore rewrote all 2 717 lines of `pycodestyle.py` into
2 095 — new line numbers, re-quoted strings, re-rendered whitespace. Two of the 77
CLI cases print a traceback or a warning that names the target's own file, line and
source text, so **77 of 100 mutants differed on the first of those cases and 75 on
the second, and 38 differed on exactly that pair**. Fifteen further "kills" sat on
lines no case executes at all.

Two more defects fell out of the same audit and are fixed in the same release:

* **The CLI observation contained the target's source.** Even with a minimal edit, a
  traceback names the file, the line and the statement, so any staged tree, any
  two-line patch and any line-shifting edit became a difference. The observation now
  projects a traceback to its exception type, message and frame names.
  `observation_schema_version` is 3.
* **An API nobody calls was invisible.** The one difference the upstream suite saw
  and the harness did not — `get_parser().add_option` — was invisible by
  construction (§5).

## 2. Corrected stage-2 mutation result

Same 100 sites (seed 21), same 86-case set after tuning (§7), one-line mutants,
both oracles: **harness 62/100 = 62.0 %** (95 % CI 52.2–70.9), **suite 74/100 =
74.0 %** (64.6–81.6).

| | both | harness only | suite only | neither |
| --- | --- | --- | --- | --- |
| corrected | **58** | **4** | **16** | **22** |
| *(v0.3, defective)* | *100* | *0* | *0* | *0* |

58 + 4 + 16 + 22 = 100; harness kills 58 + 4 = 62; suite kills 58 + 16 = 74.

No kill lands on a line no case executes, the most-frequent differing case appears
24 times rather than 77, and the four harness-only kills each have a single case
with a concrete witness. The stage-1 relationship — the harness is a subset of a
mature suite — is what the corrected stage-2 numbers show too, with one exception
worth naming: **4 mutants the suite misses, the case set catches.**

## 3. Timing: one breakdown that adds up

The v0.3 text mixed two runs: 29.1 s (pass), 0.5 s (copy) and 9.3 s (`-x` suite)
were measured separately and never summed to the quoted 32.4 s. Here is one
breakdown, from the 100-mutant run that produced §2:

| phase | total | per mutant |
| --- | --- | --- |
| tree copy + mutant write | 32.5 s | 0.32 s |
| harness pass, 86 CLI cases | 4 244.7 s | 42.45 s |
| upstream suite, full run | 1 387.7 s | 13.88 s |
| **sum** | **5 664.8 s** | **56.65 s** |
| wall clock | 94.4 min | |

The parts are not estimates: `copy` is `_write_mutant` timed on the same 100 sites
(`scripts/mutation_copy_probe.py`), `suite` is the duration each mutant's own
`tests_note` reports, and `pass` is the remainder. They sum to the recorded
per-mutant totals to 0.1 s.

The 32.4 s figure was real for the **pre-audit** run, which used `-x` and stopped
the suite at the first failure (9.3 s). The published run does not use `-x`, because
the audit needed failing-test counts: a mutant that breaks the world takes 84.5 s in
the suite alone, and that is most of the difference between 32 and 57 seconds. The
correct statement is: **a mutant costs 57 s, of which 42 s is the case set, 14 s the
suite and 0.3 s the copy** — the suite is no longer a rounding error, so a cheaper
suite invocation is what a larger sample would need.

## 4. Why the other 38 mutants survived

Both buckets classified with statement-span-aware coverage
(`scripts/mutation_audit.py`), so a site on a continuation line of a multi-line
statement counts as belonging to that statement:

| bucket | count | on a line no case executes | on a covered line, not observed | equivalent |
| --- | --- | --- | --- | --- |
| suite only (harness missed) | 16 | 5 | 11 | 0 |
| neither | 22 | 10 | 12 | **0** |

The 12 covered-but-unobserved mutants in the "neither" bucket are the only
true-equivalence candidates — if the suite and the cases both run the line and
neither sees a change, "equivalent" is a live hypothesis. All twelve were read by
hand:

| site | code | why nothing observes it | verdict |
| --- | --- | --- | --- |
| `int_plus@406:55` | `if nested or ancestor_level == 0` | `0`→`1` changes which ancestor ends the blank-line search; the fixtures never place a def at that indentation | not observed, input shape missing |
| `int_plus@584:26` | `first_row = tokens[0][2][0]` | E12x continuation; the off-by-one only matters when the first token is on row 1 | not observed, input shape missing |
| `arith_swap@585:12` | `nrows = 1 + tokens[-1][2][0] - first_row` | same statement; `nrows == 1` early return never differs on the fixtures used | not observed, input shape missing |
| `compare_swap@895:20` | `token_type == tokenize.OP` in the brace-stack guard | needs a `:` OP directly inside a `[` for `colon` handling | not observed, input shape missing |
| `compare_swap@1508:44` | `inst not in SINGLETONS` | E721 only fires for `type(x) == int`; the probes lint `x=1` | **killed by the tuning round** (§7) |
| `int_plus@1820:25` | `nrows -= 1` (diff hunk rows) | needs a `--diff` stream with a second hunk; the one probe has a single hunk | **killed by the tuning round** (§7) |
| `int_minus@1925:34` | `ord0 = ord(self.lines[0][0])` | BOM stripping only runs on a file that starts with a BOM | **killed by the tuning round** (§7) |
| `compare_swap@2029:11` | `if self.blank_before < self.blank_lines:` | needs a blank line before a continued logical line | not observed, input shape missing |
| `int_plus@2191:23` | `self.elapsed = 0` (report init) | only `--benchmark` reads it, which is declared `unstable`/`unordered` | unobservable by design |
| `return_none@2239:8` | `return self.file_errors` | `BaseReport.get_file_results()` needs a constructed reporter with a report format | not observable by the `api` kind without a factory |
| `int_minus@2428:39` | `counters['directories'] += 1` | benchmark counters only, same as `2191` | unobservable by design |
| `int_plus@2695:69` | `sys.exit(1)` in the SIGPIPE handler | needs a broken pipe mid-output | not observed, harness has no such case |

**No equivalent mutant in the sample.** The pattern is the same as stage 1: the
survivors are input shapes and output modes the case set never produced, not code
whose change cannot matter. Two of them (`2191`, `2428`) are *by design* — the
report declares `--benchmark` `unstable`/`unordered` and never normalises it away,
so a case that observed them would be measuring a field the harness promises not to
compare.

## 5. The API-surface snapshot case kind

This was missing from the v0.3 text, and it is the answer to the one thing the
harness genuinely could not see.

A CLI case runs a program. A `call` case returns a value. Neither can show an API
that nobody calls: `get_parser()` returned an object, and the migration removed
`add_option` from it — invisible to every case, caught only by the upstream suite's
`test_read_config_prefix`.

So there is a third kind. `kind: "api"` imports the module and snapshots its public
surface — public names, `inspect.signature` of every callable, class bases and
attributes, stable scalar values, the first line of the docstring — plus, when the
case names a call, the type, bases and attributes of what that call returns. Two
cases ship: `api-module` (the module surface) and `api-parser` (`get_parser()` →
`ArgumentParser`).

What that changed: the `add_option` break is no longer a suite-only finding. It is
an **approved difference with a witness** in
`docs/results/verify-change-pycodestyle-20261121.md` — `OptionParser` gone,
`argparse` added, `add_option`/`add_options`/`add_option_group` gone,
`add_argument`/`add_argument_group` added — and the oracle comparison table now
reads "both" for that row instead of "suite only".

Two decided limits, both learned by running it (ADR 004 D10x):

* an object whose `repr` carries an address becomes its type name, or the snapshot
  differs in every process;
* a snapshot may not contain the path it was imported from. `USER_CONFIG` is
  `expanduser('~/.config/pycodestyle')` evaluated at import, so two copies of
  unchanged code differed in a constant nobody touched. A behaviour-preserving
  canary found it; `HOME`, `XDG_CONFIG_HOME`, the temp directory, the workspace and
  the case directory are now replaced by markers named in the observation's
  controls.

A snapshot is still not an exercise. It shows that `add_argument` exists with a
given signature, not that it behaves; two `register_check` contracts remain the
suite's alone for that reason, and §7 of the main report says so.

### 5.1 Two silent failures found by running the held-out round

Both are the same shape as the defect this report exists for: something went wrong
in the harness, and the report said something about the *target* instead.

* **A locked case directory reported the target as opaque.** A CLI case's working
  directory is `$TMP/harness-cli/<case id>`, fixed on purpose — `-vv` prints
  "local configuration: in <dir>" and a random name made the case disagree with
  itself between two A/A passes. `rmtree(ignore_errors=True)` silently failed on a
  directory another process held, the next `mkdir` raised `FileExistsError`, and the
  outer handler classified the case `unsupported`. 55 of the 60 held-out mutants
  therefore carried two rows meaning "the target was opaque" — which is not what
  happened, and which nothing in the report could distinguish from a real opaque
  return. Removal is now retried (clearing the read-only bit, the Windows failure)
  and a surviving directory raises with its path.
* **A timed-out CLI case killed one process, not its tree.** `subprocess.run(
  timeout=...)` kills the direct child; when the pass itself is killed by the
  CPU budget, the child is orphaned. Two such orphans each burned 3 500 s of CPU
  for an hour and held those case directories open — they were the lock behind the
  finding above. The case runner now starts its own session and kills the group on
  POSIX, `taskkill /F /T` on Windows, with a test that asserts the *grandchild* is
  gone.

The first held-out run is therefore not used: it was measured with two cases
reporting `unsupported` from mutant 5 onward, which can only hide kills. The
numbers in §7 are from a clean re-run of the same 60 sites, same seed, same case
set. The discarded run happened to produce the same totals — 44/60 and 50/60, with
the same contingency table — because the two "opaque" cases never differed. It is
still discarded: a measurement in which two cases say "the target was opaque" must
not be quoted, even when its total matches, because the next one will not be so
lucky.

## 6. The CI copy phase: a fixed 10 s, not a slow disk

`docker compose`-free gate measurements on a GitHub runner showed
`copy_in_and_copy_out` = **10.146 s** for a 238 142-byte, 23-file workspace, against
**0.14 s** on this host — while `child_import` was 0.011 s against 0.03 s. A stable
10 s for a small copy is a wait, not throughput, and the review was right to read
the two-5-second signature.

It is one 10 s wait, and it is `_LOG_JOIN_TIMEOUT_SECONDS`. The container is held
open on purpose after the payload reports (the tmpfs workspace has to survive for
copy-out), so the attach socket never reaches EOF. `_LogReader.stop()` closed the
socket and then `join()`ed. On Windows the attach transport is a named pipe, where
closing the handle aborts a blocked read; on Linux it is an `AF_UNIX` socket, where
**`close()` from another thread does not wake a `recv()` blocked in the reader
thread**. The reader therefore slept until the join timeout — exactly 10 s — and
only in passes that copy a workspace in.

The fix is `shutdown(SHUT_RDWR)` before `close()`, which does deliver EOF to the
blocked read. `tests/test_sandbox.py::test_stopping_the_log_reader_wakes_a_blocked_recv`
models Linux semantics (a socket whose `read()` blocks until `shutdown()` and whose
`close()` releases nothing) and fails on the old code with a 10 s join.

**Confirmed on the runner.** The next green CI run measured, per pass
(`[this run] verdicts 30/30, byte-identical True`):

| phase | before | after |
| --- | --- | --- |
| `copy_in_and_copy_out` | 10.146 s | **0.16 s** |
| `full_pass_overhead` | 10.48 s | **0.51 s** |
| `container_create_start_teardown` | — | 0.168 s |
| `child_import` | 0.011 s | 0.02 s |

0.16 s for a 238 KB copy is a copy; 10.146 s was the join timeout. The gate still
verdicts 30/30 byte-identically, so the faster path did not change what it decides.

## 7. Tuning and held-out

Stage 2 had no tuned/held-out discipline in v0.3, because a saturated result had
nothing to measure. Now it does. The tuning round is the seven fixtures in §4 that
close the input-shape gaps — blank lines before defs, `type(x) == int`,
continuation indentation, a BOM file, a two-hunk `--diff` stream — which takes the
suite from 79 to **86 cases, hash `9ddc0ae083a5`**.

The held-out round draws 60 mutants from the **2 005 sites the published sample
never looked at** (seed 77, the 100 sampled sites excluded) and runs them against
the tuned case set with the upstream suite as the second oracle
(`docs/results/mutation-heldout-20261122.{json,md}`):

| | harness | suite | both | harness only | suite only | neither |
| --- | --- | --- | --- | --- | --- | --- |
| held-out, 60 mutants, seed 77 | **44/60 = 73.3 %** (CI 61.0–82.9) | **50/60 = 83.3 %** (CI 72.0–90.7) | 42 | 2 | 8 | 8 |
| published, 100 mutants, seed 21 | 62/100 = 62.0 % (52.2–70.9) | 74/100 = 74.0 % (64.6–81.6) | 58 | 4 | 16 | 22 |

The raw rates are not comparable — this sample is more killable for both oracles,
which is the suite's 83.3 % against 74.0 %. The comparable number is the share of
suite kills the harness also gets: **42/50 = 84.0 % held-out against 58/74 = 78.4 %
published**, against a tuning set that would have been expected to inflate it. So
the seven fixtures generalised rather than fitting the 12 survivors they were
written for; the higher raw rate is the sample, not the tuning. Two held-out
mutants are harness-only (`int_minus@2031:27` on `-v`, `int_minus@2153:31` on
`-vv`), both with a witness.

## 8. What this does not prove

* **The held-out sample is 60 mutants.** At 57 s each that is a 57-minute run and a
  Wilson interval near ±12 points; it separates "the tuning helped" from "the tuning
  did nothing", not 60 % from 65 %.
* **Two survivors are unobservable by design.** `--benchmark` is declared unstable
  and unordered; a case that observed those counters would be comparing a field the
  harness refuses to compare.
* **A mutant that makes a case hang is counted `unsupported`, not `different`.**
  `int_minus@325:24` turns `line_idx += 1` into `-= 1` in the E303 blank-line
  search, which loops forever: `fixture-e25` and `fixture-e30not` return in 1.2 s on
  the baseline and hit the case budget on the mutant, and the comparison records
  `unsupported` versus `return`, which is `undecidable`, not a kill. Measured
  directly, not inferred. So both mutation rates are **floors** for
  non-terminating mutants: the suite kills this one by timeout, the harness does
  not. Making "one tree terminated, the other did not" a difference is a
  classification change with its own report, not a footnote in this one.
* **A snapshot is not an exercise.** The `api` kind sees presence and shape, never
  behaviour.
* **Coverage moved with the case set**, from 89.74 / 82.62 / 87.11 % to **89.97 / 83.0
  / 87.4 %** (lines / branches / combined), because the seven tuning fixtures reach
  a little more of the module; `get_parser` is 25/25.
* **The corrected numbers are for `pycodestyle` 2.15.0 only.** The stage-1 result on
  `parse` (46.3 % against the suite's 86.3 %) is unchanged by this correction: all
  300 verdicts reproduced exactly after the mutator fix, which is how the defect was
  traced to stage 2 rather than to the method.

## 9. Reproduce

```
python scripts/build_cases_stage2.py --check          # 86 cases, hash 9ddc0ae083a5
python scripts/mutation_copy_probe.py                 # copy phase on the same 100 sites
python scripts/mutate.py --target .harness/verify-trees/old --module pycodestyle \
    --cases harness/cases/pycodestyle-cli.json --tests tests --tests-subdir tests \
    --seed 21 --max-mutants 100 --full-tests
python scripts/mutation_audit.py                      # why each mutant died, or did not
python scripts/mutant_evidence.py --site <site>       # one mutant's witness
python scripts/mutate.py ... --tag stage2-heldout --seed 77 --max-mutants 60 \
    --exclude-plan <the published plan>
```
