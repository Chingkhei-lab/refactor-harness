# Stage 2 — CLI observation, coverage, and the optparse→argparse migration

**Evidence, not proof of equivalence.** This document reports what these cases did
under this shim on this tree pair. It does not claim the two versions of
`pycodestyle` behave the same, and the counts and coverage lines below are the
limit of the claim, not a summary of it.

Target: **`pycodestyle` 2.15.0**. Old tree = the pinned release tag, unmodified.
New tree = the same tree with `harness/migrations/pycodestyle-argparse.patch`.

Both artifacts are hash-pinned and the module under test is proved identical
across them (`harness/oracle/pycodestyle.json`, produced by
`scripts/pin_oracle.py`):

## 1. What a `cli` case is

A stage-1 case calls a Python function. A stage-2 case **runs a program**, because
that is what a CLI migration changes. `Case` gained `kind` (`call` | `cli`),
`argv`, `stdin` and `files`; input file names are validated against absolute paths
and `..`.

The observation is a **value**:

```json
{"exit": 0, "signal": null, "stdout": "...", "stderr": "",
 "files": {"written.txt": {"size": 7, "sha256": "3733cd97..."}}}
```

`exit` is `None` when the process died from a signal and `signal` carries the
number — for a program, being killed *is* behaviour. `files` is a manifest of what
the program wrote (relative path, size, sha256), diffed against the manifest taken
before the run, so input files never appear. No timing is in the value: a duration
is nondeterministic by construction and would need a rule on every case.

Because the value goes through the ordinary encoder, rules, projections, approvals
and byte-identical comparison work on CLI cases with no special case in the
comparator.

### Environment controls

| control | value | why |
| --- | --- | --- |
| `HOME` | empty directory inside the case dir | `pycodestyle` reads `~/.pycodestyle` |
| `XDG_CONFIG_HOME` | empty directory inside the case dir | it reads `$XDG_CONFIG_HOME/pycodestyle` |
| project config | the case directory (no `setup.cfg` unless the case writes one) | discovery walks upward and would find this repo's |
| `COLUMNS` | `80` | help wraps by terminal width |
| `LANG` / `LC_ALL` | `C.UTF-8` | message locale |
| `PYTHONIOENCODING` | `utf-8` | deterministic decoding everywhere |
| stdin | the case's text, else closed | a tool waiting on input fails instead of hanging |
| TTY | none | no `isatty`-dependent formatting |
| `PATH` | `/usr/local/bin:/usr/bin:/bin` | override, never inherit (a Windows host `PATH` broke a Linux container) |
| case directory | `<tmp>/harness-cli/<case id>` | **not** `mkdtemp`: `-vv` prints the config directory, and a random name made a case disagree with itself |

`--benchmark` is declared `unstable` and `--jobs > 1` `unordered`; neither is
normalised, because normalising them would hide exactly the kind of change stage 2
exists to find.

## 4. Coverage, including the subprocess

A CLI case runs the target as a **grandchild** of the harness, so plain coverage of
the harness child sees none of the target's lines. The hook is
`COVERAGE_PROCESS_START`, installed in the shim's `sitecustomize` (already on
`PYTHONPATH`) and passed through the case environment; each subprocess writes a
parallel data file and `coverage combine` merges them. The runner also passes an
explicit `--rcfile`, because the target's own `setup.cfg` configures coverage
(`plugins = covdefaults`) and would otherwise be read from `cwd=checkout`.

`scripts/stage2_coverage.py` measures it and checks its own numbers:

| cases | lines | branches | combined | never-entered functions |
| --- | --- | --- | --- | --- |
| **77** | **1225/1365 = 89.74 %** | **660/800 = 82.5 %** | **87.07 %** | **2/89** |
| 1 (first case only) | — | — | 62.08 % | — |
| 0 | 0 covered statements | — | — | — |

The three plausibility checks all hold: one case is strictly lower than 77, an
empty set reports zero rather than crashing, and `_main` is fully covered — which
is only possible if the grandchild was traced, so the hook is working rather than
silently absent.

The migration's own surface:

| function | lines covered |
| --- | --- |
| `get_parser` | **23/23** |
| `_main` | **16/16** |
| `process_options` | 25/27 (missing 2640, 2648 — the `--diff`/reporter branches) |
| `read_config` | 37/46 (missing 2565–2580, 2608–2613 — user-config and `cli_conf` fallbacks) |

The two never-entered functions are `init_checks_registry` and
`register_check`-adjacent plugin hooks, which a command line never calls.

### What coverage does not say

89.74 % of lines is not 89.74 % of behaviour. `test_read_config_prefix` (below)
fails on a path that is **fully covered** — the line runs, the API it uses is
gone. Coverage measures execution, and this checkpoint's most important finding
is an execution-transparent break.

## 5. The migration

`harness/migrations/pycodestyle-argparse.patch` — three regions:

1. **`get_parser()`** — `OptionParser` → `ArgumentParser`; every option keeps its
   flags, `metavar`, default and help text; `type='int'` → `type=int`; `%default`
   → `%(default)s`; option groups → `add_argument_group`; `parser.config_options`
   preserved because `read_config` and third-party callers read it; a positional
   `args` is declared because argparse requires one.
2. **`read_config()`** — optparse's `parser.option_list` is replaced by
   `_option_kinds()`, which derives the same four kinds from the argparse actions;
   `parse_args([])` returns a `Namespace`; the command line is re-parsed with
   `namespace=new_options`.
3. **`process_options()`** — the lazily added `--config` uses
   `add_argument_group` plus a `_has_config_option` marker instead of
   `has_option`; the positional list comes from the declared `args`.

Decisions worth naming:

* **The public parser object is in scope** (ADR 005 D2): `get_parser()` still
  returns a parser and `process_options` still accepts an injected one; what
  changes is the class of the object, which is what a parser swap is.
* **`--version` output is unchanged.** An earlier draft prefixed the program name
  (`pycodestyle 2.15.0`), argparse's habit and not optparse's. The case set caught
  it (`probe-version` differed), it was fixed, and it is **not** approved.
* **`-1` as a value still works**: `--max-line-length -1` behaves identically on
  both trees, measured.

## 6. verify-change: 77 cases, two rounds, alternating order

exactly what was accepted: the same `ValueError` from `configparser.getint`, the
same frames, the same message — and different line numbers because the patch adds
41 lines. Approving the traceback's line numbers is not approving the crash; the
crash is pre-existing in both versions and is reported as such.

### The report that caught the `--version` bug

`docs/results/verify-change-pycodestyle-20261120-argparse-prefix.json` is the
**pre-fix** report, kept as evidence. It was produced by re-applying the prefix to
the migrated tree and running the same command, because the original run wrote to
the same report path and was overwritten. In it:

* `probe-version` is `different` and **unapproved** (`2.15.0` vs
  `pycodestyle 2.15.0`) — the bug the cases caught, still visible;
* the two line-number approvals are **stale**, because the prefix adds two lines
  and therefore moves every traceback and warning line number again. That is the
  staleness rule doing its job: an approval cannot follow a change it was not
  written for.

The fixed migration's report is `…-argparse.json`; this one is kept because a
harness that can only show its successes is not one you can audit.

## 7. The upstream suite against the harness

The comparison the second oracle exists for. Four upstream tests fail on the
migrated tree; eight harness cases differ. Classified:

| difference | harness case | upstream suite | seen by |
| --- | --- | --- | --- |
| help/usage layout (`usage:` vs `Usage:`, blank line) | `probe-help` | `test_shell.py::test_print_usage` (line 60) | **both** |
| empty command line error text | `probe-no-args` | `test_shell.py::test_check_noarg` (123), `test_shell.py::test_check_diff` (192) | **both** |
| invalid integer wording | `probe-int-error` | — | **harness only** |
| unknown-option wording | `probe-unknown` | — | **harness only** |
| `--jobs` rejected with the value echoed | `probe-jobs` | — | **harness only** |
| `--max-blank-lines` rejected | `probe-blank-lines` | — | **harness only** |
| traceback line numbers | `probe-config-int-error` | — | **harness only** |
| deprecation-warning line number | `probe-deprecated-section` | — | **harness only** |
| **`get_parser().add_option` no longer exists** | **(no case)** | `test_pycodestyle.py::test_read_config_prefix` | **suite only** |

That one suite-only row is the finding of this checkpoint:

* The harness compares **behaviour through the command line**, so it sees text and
  exit status. It does not see the *shape of the object* `get_parser()` returns,
  because no case calls the parser as an API.
* The suite calls `parser.add_option('--config')` directly — an optparse-only
  method — and fails with `AttributeError: 'ArgumentParser' object has no
  attribute 'add_option'`.
* Every line that test executes is **covered** by the CLI cases. Coverage is a
  prior, not a detector.

The honest reading: on this change the harness found 6 behavioural differences the
suite does not assert, and missed 1 API break the suite finds. A harness that
observes a program cannot see an API that no program calls — that is a limit of
the entry kinds (ADR 005 D1), not a bug, and it is why the `api` entry kind exists
in the ADR for stage 3.
