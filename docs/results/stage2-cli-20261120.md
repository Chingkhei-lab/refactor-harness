# Stage 2 — the CLI observation layer, and the optparse→argparse migration

**Evidence, not proof of equivalence.** This document reports what the cases did
under this shim on this tree pair. It does not claim the two versions of
`pycodestyle` behave the same, and the counts below are the limit of the claim,
not a summary of it.

Target: **`pycodestyle` 2.15.0**, pinned by hash. Old tree = the release tag
unmodified. New tree = the same tree with `harness/migrations/pycodestyle-argparse.patch`
applied.

---

## 1. What a `cli` case is

A stage-1 case calls a Python function. A stage-2 case **runs a program**, because
that is what a CLI migration changes. `Case` gained:

| field | meaning |
| --- | --- |
| `kind` | `call` (stage 1, unchanged) or `cli` |
| `argv` | the arguments, exactly as typed — abbreviations, `--`, repeats |
| `stdin` | text fed on stdin; empty means closed stdin |
| `files` | input files, relative paths only, written into the case directory |

Validation refuses any input file name that is absolute or contains `..`, so a
case file cannot write outside its own directory even before the sandbox sees it.

The observation is a **value**, not an exception:

```json
{"exit": 0, "signal": null,
 "stdout": "...", "stderr": "",
 "files": {"written.txt": {"size": 7, "sha256": "3733cd97..."}}}
```

* `exit` is `None` when the process died from a signal, and `signal` then carries
  the number — for a CLI, "killed by SIGSEGV" is behaviour, not a harness bug.
* `files` is a manifest of the files the program *wrote*, relative path, size and
  sha256, computed after the run and diffed against the manifest before it. Input
  files therefore never appear, and an unchanged file never appears.
* No timing is in the value. A duration is nondeterministic by construction and
  would need a rule on every case; the pass duration is in the report.

Because the value goes through the ordinary encoder, rules, projections,
approvals and byte-identical comparisons all work on CLI cases without special
cases in the comparator.

### Environment controls

Every `cli` case runs with:

| control | value | why |
| --- | --- | --- |
| `HOME` | an empty directory inside the case dir | `pycodestyle` reads `~/.pycodestyle` |
| `XDG_CONFIG_HOME` | empty directory inside the case dir | `pycodestyle` reads `$XDG_CONFIG_HOME/pycodestyle` |
| project config | the case directory, which holds no `setup.cfg`/`tox.ini` unless the case writes one | config discovery walks upward and would otherwise find this repo's |
| `COLUMNS` | `80` | help text wraps by terminal width |
| `LANG` / `LC_ALL` | `C.UTF-8` | message locale |
| `PYTHONIOENCODING` | `utf-8` | deterministic decoding on every platform |
| stdin | the case's text, else closed | a tool waiting on input fails instead of hanging |
| TTY | none (pipes) | no isatty-dependent formatting |
| `PYTHONPATH` | shim, harness sources, target tree (in the sandbox: tmpfs paths) | nothing points at a host path |
| `PATH` | `/usr/local/bin:/usr/bin:/bin` | **override, never inherit** (see findings F2) |

`--jobs > 1` is never used; the case set declares it `unordered` instead of
normalising its output away. `--benchmark` is declared `unstable` for the same
reason: the number it prints is a measurement, not a behaviour, and pretending
otherwise would mean a rule that hides a real change.

## 2. The case set

`harness/cases/pycodestyle-cli.json` — **61 cases**, case-set hash
**`5b86bc8dab70b2f1`**, regenerated by `scripts/build_cases_stage2.py`, which
`--check`s it against the pinned tree so a stale file cannot be committed.

| source | count | what it is |
| --- | --- | --- |
| `testing/data` | 42 | first 40 lines of every fixture in the target's own test data |
| `options/<dimension>` | 19 | one case per option-matrix dimension |

**Inputs only.** The fixtures are read for their code, never for the annotated
expected codes that sit in the same files, so the case set cannot inherit the
suite's answers. The excerpt is 40 lines, not the whole file, to keep the case
file reviewable (40 KB) — the cost is real code with real violations rather than
maximum coverage of each fixture.

The option probes, each naming its dimension:

| dimension | what it exercises |
| --- | --- |
| `long-help` / `version` | the two exit-0 informational paths |
| `abbreviated-long-option` | `--max-line-len=79`, which both parsers accept |
| `double-dash-then-filename` | `--` followed by a name that looks like an option |
| `negative-number-as-value` | `--max-line-length=-1` |
| `repeated-option-last-wins` | two `--select` flags |
| `clustered-short-flags` | `-qq` |
| `invalid-value-for-choice` | `--format=not-a-format` |
| `non-integer-where-int-expected` | `--max-line-length=abc` |
| `no-options-default-behaviour` | the defaults, with no flags at all |
| `dash-reads-stdin` | `-` with stdin text |
| `unknown-option` / `file-does-not-exist` | error paths |

| `declared-unstable-benchmark` | `--benchmark`, declared unstable |
| `declared-unordered-jobs` | `--jobs=1`, declared unordered |

The selection is fixed — no sampling — so the file and its hash are reproducible
from the pinned tree.

## 3. A/A: does a CLI case agree with itself?

Four passes of the **same** tree over the 61 cases: two fixed-order, two
shuffled (seeds 5 and 9, so ordering effects land on position, not on version).

| pass | cases | non-`return` | differences vs pass 1 |
| --- | --- | --- | --- |
| fixed #1 | 61 | 0 | — |
| fixed #2 | 61 | 0 | **0** |
| shuffled (seed 5) | 61 | 0 | **0** |
| shuffled (seed 9) | 61 | 0 | **0** |

So `harness/rules/pycodestyle.json` ships **0 rules**, for the same reason
`parse` does: the result is 0 noise, not 0 effort. A case that varied here would
have been marked `flaky` and removed from the comparison's evidence.

One test-side ordering assumption was caught by CI rather than here: the env-control
test compared `os.listdir(HOME)` to a literal list, and ext4 returned `tmp` before
`.config`. It is sorted now. The observation itself never depended on it — but a
control check that is itself order-dependent is a control you cannot cite.

The rule the case set would need if this ever changes is a path rule: an error
message that names the case directory would embed a temp path. The environment
controls are what keep that out, and `probe-file-does-not-exist` is the case that
would expose it first.

## 4. The migration

`harness/migrations/pycodestyle-argparse.patch` — 233 diff lines, three regions:

1. **`get_parser()`** — `OptionParser` → `ArgumentParser`. Every option keeps its
   flags, `metavar`, default and help text; `type='int'` becomes `type=int`;
   `%default` in the help strings becomes `%(default)s`; the "Testing Options"
   and "Configuration" groups become `add_argument_group`; `parser.config_options`
   is preserved because `read_config` and third-party callers read it.
2. **`read_config()`** — optparse's `parser.option_list` (dest → `type or action`)
   is replaced by `_option_kinds()`, which derives the same four kinds from the
   argparse actions. `parser.parse_args([])` returns a `Namespace` directly, and
   the command line is re-parsed with `namespace=new_options` instead of
   `values=new_options`.
3. **`process_options()`** — the lazily added `--config` option uses
   `add_argument_group` and a `_has_config_option` marker instead of
   `has_option`. `parse_args` returns a namespace, so the positional list comes
   from the declared `args` field.

Decisions worth naming:

* **The public parser object is in scope** (ADR 005 D2). `get_parser()` still
  returns a parser and `process_options` still accepts an injected one, so the
  library surface is preserved; what changes is the class of the object it
  returns, which is exactly what a parser swap is.
* **`--version` output is unchanged.** An earlier draft prefixed the program name
  (`pycodestyle 2.15.0`), which is argparse's habit but not optparse's. The case
  set caught it: `probe-version` is one of the 19 probes, and it differed. That
  is the **unintended behaviour change** this checkpoint found, and it is fixed
  and re-verified rather than approved.
* **`-1` as a value still works.** `--max-line-length -1` (space-separated) is a
  classic argparse trap; argparse only treats it as a value when the parser has
  no options that look like negative numbers, which holds here. Measured on both
  trees: identical findings.

### Upstream suite on the migrated tree

`763 passed, 12 skipped` before the migration; after it, **4 failures**:

| test | classification |
| --- | --- |
| `test_shell.py::test_print_usage` | asserts `stdout.startswith("Usage: ...")`; argparse prints `usage:` |
| `test_shell.py::test_check_noarg` | asserts the exact two-line `Usage:`/`error:` shape |
| `test_shell.py::test_check_diff` | same usage-text assertion |
| `test_pycodestyle.py::test_read_config_prefix` | calls `parser.add_option('--config')`, an optparse-only method |

The first three are the approved text class. The fourth is the honest cost of the
change and is **not** approved away: `get_parser()` no longer supports
`add_option`, so any third-party code that mutates the parser (flake8 builds its
own, but the pattern exists) breaks. It is reported as an unintended consequence
of the migration, in the same category as the `--version` regression — the
difference is that this one is inherent to argparse and was kept deliberately,
while the `--version` one was not.

Also measured: the migrated tree passes its own linter (`pycodestyle
pycodestyle.py` reports nothing) — the new code is written in the style the tool
enforces, which `test_all.py::test_own_dog_food` checks.

## 5. verify-change: what the two trees actually did

`scripts/verify_change.py --old …/old --new …/new --module pycodestyle
--cases harness/cases/pycodestyle-cli.json`

Order: A/A on the old tree, then **old, new, old, new**. Rules: 0. Approvals:
`harness/approvals/pycodestyle.json`, sha256 `e7a7d5cfbee02798…`.

| measurement | value |
| --- | --- |
| case set | 61 cases, sha256 `5b86bc8dab70b2f1…` |
| verdicts (2 rounds × 61 cases) | 122 |
| identical | **112** |
| different (approved) | **10** |
| different (unapproved) | **0** |
| equivalent / equivalent_bounded | 0 |
| unsupported | 0 |
| flaky | 0 |
| stale approvals | 0 |

Five distinct cases differ, each in both rounds (so 10 verdicts):

| case | path | difference |
| --- | --- | --- |
| `probe-help` | `$.value.stdout` | help layout: `usage:` case, a positional-arguments section, `options:` instead of `Options:` |
| `probe-int-error` | `$.value.stderr` | `argument --max-line-length: invalid int value` vs `option … invalid integer value` |
| `probe-unknown` | `$.value.stderr` | `unrecognized arguments: --no-such-option` vs `no such option` |
| `probe-jobs` | `$.value.stderr` | same wording, and the value is echoed (`--jobs=1`) |
| `probe-blank-lines` | `$.value.stderr` | same wording for a non-existent option |

Every one is parser **text** with the exit status unchanged (2), which is why
each is approved with a reason and a reviewer rather than normalised: a rule
would say "these two are equivalent", and for `--help` that is false — the help
*is* different, and a reader of the report should see it.

`probe-version` is **absent** from this table. It differed before the fix and is
byte-identical after it, which is the one line that shows the case set doing its
job.

## 6. What is not done

* **Stage-2 mutation.** The protocol is written down (ADR 005 D7: fixed seed,
  first pass, tuned, held-out, upstream suite as the second oracle, stage-1 tuning
  discipline) but not run. Nothing in this document depends on it.
* **Subprocess coverage.** `COVERAGE_PROCESS_START` + a `sitecustomize.py` in the
  shim directory is the mechanism that would let a CLI case contribute to the
  coverage numbers; the coverage figures quoted for stage 1 are for the direct
  call path and are **not** claimed for stage 2. This is the next task before the
  final report, because a stage-2 report without coverage numbers would be
  quoting a limit it has not measured.
* **`tag v0.3`.** Not tagged. The CLI layer, approvals, case set, A/A and the
  migration exist and are verified; the mutation results that the final report
  needs do not.
