## The containment matrix (what the kernel enforces)

Run container — the hardening profile from ADR
[`003-sandbox.md`](../adr/003-sandbox.md) D1, pinned by tests and verified by
the 18-case hostile suite (18/18 green) plus the 6-case install-hostile suite
(6/6 green):

| Control | Enforcement |
| --- | --- |
| Network | `network_mode: none` — no interfaces, no DNS |
| Identity | `user 65534:65534` (nobody:nogroup), `cap_drop ALL`, `no-new-privileges` |
| Filesystem | read-only rootfs; workspace is a tmpfs (`nosuid,nodev`, uid 65534, mode 0755, size-capped); `/tmp` tmpfs `size=16m,noexec,nosuid,nodev` |
| Memory | `mem_limit` with `memswap_limit == mem_limit` (no swap) → cgroup OOM kill; tmpfs pages are charged to the same cgroup, so a tmpfs-fill dies by OOM before ENOSPC (measured in the hostile suite) |
| CPU | `nano_cpus` quota (default 1.0 CPU) |
| Processes | `pids_limit` |
| Disk/output | `nofile` + `fsize` ulimits; daemon-side json-file log cap; runner-side output truncation with digests |
| Verdict boundary | everything the container reports is untrusted input; host-side evidence (cgroup `memory.events` oom counter, deadlines, exit markers) decides what happened |
| Janitor | label-scoped sweeps: age-based global sweep + per-job attempt sweep before every retry |

Install container (ADR 003 D2): identical profile with exactly two deltas —
`network_mode: bridge` (pip needs the index; this is the ONLY networked
container in the pipeline) and commit at `docker commit` time (the deps layer
must bake; a tmpfs deps dir would commit nothing). Base image is pinned to a
registry digest before anything derives from it. pip runs with
`--require-hashes` (a wheel with a wrong/wrong-format hash is refused
permanently) and `--no-cache-dir`. Cross-process coordination on one daemon
is a local file lock: `inspect → lock → double-check → build`; the kernel
releases the lock if a builder is SIGKILL'd and the waiter's bound is sized
above the builder's wall clock.

## Concurrency ramp (host capacity)

12 simultaneous sandboxes at 256 MiB each, n = 1…12, all clean (p50
2.89 s → 5.09 s; no wall or memory failure at any n). The ramp was capped at
12, so the measured host maximum is ≥ 12. The per-worker default
`ENGINE_MAX_CONCURRENT_SANDBOXES=4` sits below it on purpose: with 3 workers
the engine draws at most 3 × 4 = 12 ≤ host max, leaving headroom for the
daemon, Postgres, and the janitor.

## Kill demo (single cycle, end to end)

Payload sleeps 20 s; the worker is hard-killed mid-run:

1. one orphan container remains after the kill (expected: the daemon keeps
   running the container its client abandoned);
2. the retry's attempt sweep + janitor remove it: `removed=1`, 0.828 s;
3. the workflow re-drives from the lease expiry and **succeeds 41.6 s after
   the kill**;
4. `sandbox_runs` keeps exactly ONE row — the committing attempt 2 (killed
   attempts leave no row: measurements, not effects);
5. zero `engine-sandbox` containers left at the end.

## Mini-chaos: the kill loop against real sandboxes

200 `sandbox-test-run` workflows (4 jobs each, 800 jobs), 3 workers, a random
worker hard-killed every 3–6 s and replaced; the A→B→A→B regression tests
(`test_crash_mid_step_resumes_at_that_step`,
`test_committed_step_is_not_rerun`) run FIRST because their `clean_db`
fixture truncates the test database.

| | Run 1 | Run 2 | Run 3 (final, cap 4500 s) |
| --- | --- | --- | --- |
| Config | lease 4 s, reaper 1 s, 20-min drain timeout | lease 2 s, reaper 0.5 s, 40-min timeout, **step budget 5** | same knobs, **step budget 40** (`ENGINE_SANDBOX_STEP_BUDGET`) |
| Drained | **no** (timed out) | **yes**, 2210.7 s | **yes**, 2786.2 s |
| Kills / mid-job kills | 233 / 232 | 440 / 428 | 553 / 543 |
| Outcome | 48 succeeded, 152 still running | 158 succeeded, 42 failed | **200 succeeded, 0 failed** |
| Max step attempts | 2 | 5 (budget exhausted) | **24** (budget 40 — headroom held) |
| `sandbox_runs` rows (= succeeded) | 48 | 158 | 200 |
| Duplicate `(job_id, attempt)` rows | 0 | 0 | 0 |
| Orphan run rows | 0 | 0 | 0 |
| Janitor pass | removed 107, leftovers `[]` | removed 36, leftovers `[]` | **removed 0** — the per-attempt sweeps left nothing |
| Regression tests | pass | pass (rc=0) | pass (rc=0) |

**Run 1 → run 2 diagnosis (why only knobs changed).** Run 1's machinery was
fully correct (0 failed, 0 duplicates, janitor clean) but it did not drain:
200 in-flight workflows over 3 workers (Little's law: each workflow's 4
sequential jobs queue behind ~200 others at ~0.4–0.6 jobs/s effective — every
murder costs a lease-expiry wait) put workflow wall time at ~16 min median,
over the 20-min timeout. Halving the lease, halving the reaper interval, and
sizing the timeout to the measured service rate keeps the kill spec
(3–6 s, 3 workers, 200 workflows) untouched.

**Run 2's 42 failures are the engine working as designed.** The attempts
histogram shows why: 606 first-attempt successes, then a long murder tail
(2:47, 3:30, 4:21) ending at 5:54 — 42 workflows whose budget was exhausted
by mid-job kills were dead-lettered by the reconciler (`dead_steps` actions
in the log), each with its `dead_letters` row. A murdered job costs an
attempt like any other failure; with the authored budget of 5, a
3–6 s bombardment over 37 minutes can plausibly eat 5 attempts of one
workflow. The task-spec gates all passed in run 2 (all terminal, zero
leftovers, no duplicates, one row per succeeded workflow, regression tests);
only the experiment's own stricter "all succeeded" gate failed.

**Run 3's fix — budget sized for the bombardment.** A new
`ENGINE_SANDBOX_STEP_BUDGET` env knob (applied via `dataclasses.replace` on
`StepDef.max_attempts` inside the SHARED handlers module, so worker-side and
caller-side definition snapshots agree) widens the retry budget to 40 for the
bombardment run. Unset, the authored default (5) holds.

**Run 3, attempt 1 — the budget fix is proven, the cap was not.** Every
durability invariant held again (0 duplicates, 0 orphans, 0 leftovers, 0
failed, regression tests green) and the murder tail now runs 2:48, 3:30,
4:22, 5:15, 6:10, 7:21, 8:7 instead of dying at 5. But the 2400 s cap was
sized off run 2's duration, and run 2 had hidden help: its 42 dead-lettered
workflows LEFT the queue early. With no early exits, the same ~0.3 useful
jobs/s must carry all 800 jobs plus every murder-wasted attempt, which needs
~2600–2800 s. Attempt 1 stopped at 175/200 succeeded (preserved as
`…-budget40-nondrained.json`); the drain cap became 4500 s — generous on
purpose, because the drain check exits the moment the queue is empty.

**Run 3, final — all eight gates PASS.** 200/200 succeeded in 2786.2 s
(inside the predicted 2600–2800 s window), 553 kills / 543 mid-job, zero
duplicates, zero orphans, zero leftover containers, one `sandbox_runs` row
per succeeded workflow, regression tests green. The attempts histogram is
the budget-sizing evidence: 650 clean first attempts, then a murder tail
stretching 2, 3, 4 … 18, **24** — the last workflow in flight absorbed 23
consecutive murders, because as the pool drains every kill lands on one of
the few remaining jobs. Budget 40 held with headroom; the authored 5 would
have dead-lettered it (run 2's failure mode). The janitor's final pass
removed **0** containers: the per-attempt sweeps inside the run step left
nothing for it to find.

## docker-py 7.2 stream finding

docker-py 7.2.0's `logs()` demuxes/buffers client-side, so it cannot serve the
runner's live-streaming contract. The runner instead attaches its own raw
socket BEFORE the container starts and demultiplexes the docker stream frames
itself (`_demux` hardened against short/fragmented reads). Verified on a real
daemon: `OBSERVED stream separation: stdout='OUT-tail' stderr='ERR-line'`.
