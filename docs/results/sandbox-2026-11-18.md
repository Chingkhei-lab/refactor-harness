## The containment matrix (what the kernel enforces)

Run container — the hardening profile from ADR
[`003-sandbox.md`](../adr/003-sandbox.md) D1, pinned by tests and verified by
the 18-case hostile suite (18/18 green) plus the 6-case install-hostile suite
(6/6 green):

| Control | Enforcement |
| --- | --- |
| Network | `network_mode: none` — no interfaces, no DNS |
| Identity | `user 65534:65534` (nobody:nogroup), `cap_drop ALL`, `no-new-privileges` |
| Filesystem | read-only rootfs; workspace is a tmpfs (`nosuid,nodev`, uid 65534, mode 0755, size-capped); `/tmp` tmpfs `size=16m,noexec,nosuid,nodev` |
| Memory | `mem_limit` with `memswap_limit == mem_limit` (no swap) → cgroup OOM kill; tmpfs pages are charged to the same cgroup, so a tmpfs-fill dies by OOM before ENOSPC (measured in the hostile suite) |
| CPU | `nano_cpus` quota (default 1.0 CPU) |
| Processes | `pids_limit` |
| Disk/output | `nofile` + `fsize` ulimits; daemon-side json-file log cap; runner-side output truncation with digests |
| Verdict boundary | everything the container reports is untrusted input; host-side evidence (cgroup `memory.events` oom counter, deadlines, exit markers) decides what happened |
| Janitor | label-scoped sweeps: age-based global sweep + per-job attempt sweep before every retry |

Install container (ADR 003 D2): the run phase's profile with exactly two
deltas — `network_mode: bridge` (pip needs the index; this is the ONLY
networked container in the pipeline) and **`read_only: False`** (the writable
layer IS the product). Base image is pinned to a
registry digest before anything derives from it. pip runs with
`--require-hashes` (a wheel with a wrong/wrong-format hash is refused
permanently) and `--no-cache-dir`. Cross-process coordination on one daemon
is a local file lock: `inspect → lock → double-check → build`; the kernel
releases the lock if a builder is SIGKILL'd and the waiter's bound is sized
above the builder's wall clock.

## Install phase

Cache key `install_key = sha256("engine-deps-v1" ∥ base_digest ∥ requirements
bytes)` — domain-separated, requirements first. The six pinned wheels
(`six==1.16.0 --hash=sha256:8abb2f…`) are exactly what pip measured.

| Measurement | Value |
| --- | --- |
| Install key | `8546de2b3338d7c3…95f78` |
| Resulting image | `sha256:2e1cce4fb50d…192eb` |
| Base image / digest | `python:3.12-slim` @ `5e2bdb1b0d54…4fa5b` |
| Cold build (image absent) | 10.031 s |
| Cached lookup (key hit, image exists) | 0.234 s — returns the SAME image ID |
| Permanent refusals | wrong-hash wheel → `pip_failed`; oversized pins → `too_large`; missing base → `base_image_missing` (hostile suite, all retried correctly when transient) |

**What the install container mounts, and what `commit()` captures.** There are
NO bind mounts and NO volumes, so the only writable places are the container's
own overlay layer and one tmpfs:

| Path | Kind | Baked into the image? |
| --- | --- | --- |
| `/` | overlay upper layer (`read_only: false`) | yes (only what is written) |
| `/var/tmp/engine-requirements.txt` | file PUT before start into the layer | yes — the pins travel with the image (provenance) |
| `/var/tmp/deps/**` | `pip --target` output directory in the layer | yes — this IS `PYTHONPATH` for the run phase |
| `/tmp` | tmpfs `size={tmp_mb}m,noexec,nosuid,nodev,mode=1777` | **no** — tmpfs is invisible to `commit()`; pip scratch never bakes |

`pip install … --target /var/tmp/deps` means pip never touches site-packages:
the deps directory is the only payload. `/var/tmp` is an FHS world-writable
sticky directory, so the non-root user (`65534:65534`) can create it there.
`docker commit` captures the container's writable layer **only** — not tmpfs,
not volumes. The rejected design was (read-only rootfs + deps in a tmpfs):
`commit()` captures neither, so it would produce an EMPTY image. The accepted
design is (writable rootfs + tmpfs scratch): the layer is the product, the
scratch is deliberately excluded. The run container then starts `FROM`
`engine-deps:<key>` with `read_only: True` and `PYTHONPATH=/var/tmp/deps` —
it only reads.

**Image identity per run.** Every `sandbox_runs` row carries `image` and
`install_image` (migration 0008), populated from the install step's output:
the image ID that run actually used. Sample from the final mini-chaos run
(200 rows, attempt 2): `image = install_image = sha256:2e1cce4f…`,
`install_cached = t`, `exit_code = 0`. Rebuilds are **functionally
equivalent, not byte-identical** — layer timestamps differ between two builds
of the same pins — so the recorded ID is the truth and "functionally
equivalent" is the honest claim (ADR 003 D2).

## Concurrency ramp (host capacity, measured past the demo's n = 12)

256 MiB sandboxes, 2 s sleep payload, barrier start, no workspace.
`scripts/sandbox_demo.py` ramps to n = 12; `scripts/sandbox_ramp_max.py`
continues the ladder until a level fails, which is what "maximum" means.

| n | Runner deadline | Result | p50 | Wall |
| --- | --- | --- | --- | --- |
| 1…12 | 25 s | clean (demo ramp) | 2.89 → 5.09 s | — |
| 14, 16, 20, 24, 32, 48, 64 | 25 s | clean | 5.36 → 16.08 s | 5.5 → 18.0 s |
| 80 | 25 s | clean | 20.69 s | 22.1 s |
| 96 | **25 s** | **FAIL — 6 of 96 exit 137** | 24.4 s | 27.4 s |
| 80, 88, 96 | **60 s** | **clean, 2 repeats each** | 23.9 → 59.2 s | 28.5 → 66.2 s |
| 96, 128 | **60 s** | **clean** (96 a 3rd time; 128 once) | 32.8 s, 38.8 s | 38.8 s, 44.5 s |

**What this actually says: there is no host memory wall at 128.** The only
failure ever observed was at n = 96 under a 25 s runner deadline, and it did
not reproduce — with the deadline at 60 s, n = 96 was clean three times and
n = 128 clean once (`sandbox-ramp-20261118.json`). Latency, not count, is what
scales: p50 climbs 2.9 s → 59.2 s across the ladder. The 3.83 GiB VM is
nowhere near exhausted by 128 idle 2 s-sleep containers, which is why the
count wall was never reached; the binding constraint in this range is the
per-sandbox wall clock.

**The 96 failure was the deadline, not memory.** Its p50 was 24.4 s against a
25 s wall and its six victims exited 137 with no completion marker — exactly
what the runner's own deadline kill looks like (`timed_out`, a different field
from `oom_killed`, which the script that produced that number did not print).
The earlier reading ("the Docker VM OOM-killed them") rested on
`State.OOMKilled = false` alone; raising the deadline to 60 s removed the
failures entirely, which is the evidence the inference was missing. Residual
unknown: a 137 with no marker leaves no readable cgroup counter (ADR 003 D7
rule 3), so "deadline" is the supported explanation, not a probe-level proof.

**Caveats on the absolutes.** The payload is a 2 s `time.sleep`, so the ramp
measures daemon/VM capacity for container *count*, not the memory a workspace
tmpfs charges to the cgroup (D4). Repeated levels also drifted (n = 80 p50:
20.7 s originally, 23.9 s and 33.4 s in the repeats), so the box was not quiet:
treat the clean/fail verdict as the datum and the absolute seconds as
indicative.

**Policy.** `ENGINE_MAX_CONCURRENT_SANDBOXES=4` × 3 workers = 12 concurrent is
~9 % of the highest measured-clean level (128). It is headroom chosen below a
measured ceiling, not a value derived from one — and because the ceiling is
latency-bound rather than memory-bound, the small default is as much about
queue fairness as about memory.

## Kill demo (single cycle, end to end)

Payload sleeps 20 s; the worker is hard-killed mid-run:

1. one orphan container remains after the kill (expected: the daemon keeps
   running the container its client abandoned);
2. the retry's attempt sweep + janitor remove it: `removed=1`, 0.828 s;
3. the workflow re-drives from the lease expiry and **succeeds 41.6 s after
   the kill**;
4. `sandbox_runs` keeps exactly ONE row — the committing attempt 2 (killed
   attempts leave no row: measurements, not effects);
5. zero `engine-sandbox` containers left at the end.

## Mini-chaos: the kill loop against real sandboxes

200 `sandbox-test-run` workflows (4 jobs each, 800 jobs), 3 workers, a random
worker hard-killed every 3–6 s and replaced; the A→B→A→B regression tests
(`test_crash_mid_step_resumes_at_that_step`,
`test_committed_step_is_not_rerun`) run FIRST because their `clean_db`
fixture truncates the test database.

| | Run 1 | Run 2 | Run 3 (final, cap 4500 s) |
| --- | --- | --- | --- |
| Config | lease 4 s, reaper 1 s, 20-min drain timeout | lease 2 s, reaper 0.5 s, 40-min timeout, **step budget 5** | same knobs, **step budget 40** (`ENGINE_SANDBOX_STEP_BUDGET`) |
| Drained | **no** (timed out) | **yes**, 2210.7 s | **yes**, 2786.2 s |
| Kills / mid-job kills | 233 / 232 | 440 / 428 | 553 / 543 |
| Outcome | 48 succeeded, 152 still running | 158 succeeded, 42 failed | **200 succeeded, 0 failed** |
| Max step attempts | 2 | 5 (budget exhausted) | **24** (budget 40 — headroom held) |
| `sandbox_runs` rows (= succeeded) | 48 | 158 | 200 |
| Duplicate `(job_id, attempt)` rows | 0 | 0 | 0 |
| Orphan run rows | 0 | 0 | 0 |
| Janitor pass | removed 107, leftovers `[]` | removed 36, leftovers `[]` | **removed 0** — the per-attempt sweeps left nothing |
| Regression tests | pass | pass (rc=0) | pass (rc=0) |

**Run 1 → run 2 diagnosis (why only knobs changed).** Run 1's machinery was
fully correct (0 failed, 0 duplicates, janitor clean) but it did not drain:
200 in-flight workflows over 3 workers (Little's law: each workflow's 4
sequential jobs queue behind ~200 others at ~0.4–0.6 jobs/s effective — every
murder costs a lease-expiry wait) put workflow wall time at ~16 min median,
over the 20-min timeout. Halving the lease, halving the reaper interval, and
sizing the timeout to the measured service rate keeps the kill spec
(3–6 s, 3 workers, 200 workflows) untouched.

**Run 2's 42 failures are the engine working as designed.** The attempts
histogram shows why: 606 first-attempt successes, then a long murder tail
(2:47, 3:30, 4:21) ending at 5:54 — 42 workflows whose budget was exhausted
by mid-job kills were dead-lettered by the reconciler (`dead_steps` actions
in the log), each with its `dead_letters` row. A murdered job costs an
attempt like any other failure; with the authored budget of 5, a
3–6 s bombardment over 37 minutes can plausibly eat 5 attempts of one
workflow. The task-spec gates all passed in run 2 (all terminal, zero
leftovers, no duplicates, one row per succeeded workflow, regression tests);
only the experiment's own stricter "all succeeded" gate failed.

**Run 3's fix — budget sized for the bombardment.** After run 2 the step
budget was raised from 5 to **40** (`ENGINE_SANDBOX_STEP_BUDGET`), because 428
mid-job kills had exhausted the authored 5-attempt budget and dead-lettered 42
healthy workflows — a murdered job costs an attempt like any other failure.
With 40 the final run absorbed a 24-attempt murder victim. That 40 is a
**bombardment setting, not an operating point**: 553 kills over 200 workflows
produced a 24-attempt step only because, as the pool drains, every remaining
kill lands on one of the few jobs still in flight. A new
`ENGINE_SANDBOX_STEP_BUDGET` env knob (applied via `dataclasses.replace` on
`StepDef.max_attempts` inside the SHARED handlers module, so worker-side and
caller-side definition snapshots agree) widens the retry budget to 40 for the
bombardment run. Unset, the authored default (5) holds.

**Run 3, attempt 1 — the budget fix is proven, the cap was not.** Every
durability invariant held again (0 duplicates, 0 orphans, 0 leftovers, 0
failed, regression tests green) and the murder tail now runs 2:48, 3:30,
4:22, 5:15, 6:10, 7:21, 8:7 instead of dying at 5. But the 2400 s cap was
sized off run 2's duration, and run 2 had hidden help: its 42 dead-lettered
workflows LEFT the queue early. With no early exits, the same ~0.3 useful
jobs/s must carry all 800 jobs plus every murder-wasted attempt, which needs
~2600–2800 s. Attempt 1 stopped at 175/200 succeeded (preserved as
`…-budget40-nondrained.json`); the drain cap became 4500 s — generous on
purpose, because the drain check exits the moment the queue is empty.

**Run 3, final — all eight gates PASS.** 200/200 succeeded in 2786.2 s
(inside the predicted 2600–2800 s window), 553 kills / 543 mid-job, zero
duplicates, zero orphans, zero leftover containers, one `sandbox_runs` row
per succeeded workflow, regression tests green. The attempts histogram is
the budget-sizing evidence: 650 clean first attempts, then a murder tail
stretching 2, 3, 4 … 18, **24** — the last workflow in flight absorbed 23
consecutive murders, because as the pool drains every kill lands on one of
the few remaining jobs. Budget 40 held with headroom; the authored 5 would
have dead-lettered it (run 2's failure mode). The janitor's final pass
removed **0** containers: the per-attempt sweeps inside the run step left
nothing for it to find.

**Janitor coverage — what was actually exercised.** The age-based global sweep
has been exercised end to end exactly once, in the kill demo (one orphan,
0.828 s), plus run 1's post-mortem pass (107 containers) and run 2's (36). In
the final run it removed **0** because the per-attempt sweep that runs before
every retry had already removed the orphan. So the janitor is *proven* as a
backstop for a single abandoned container, and *largely unexercised at scale* —
the final run's 0 is a statement about the per-attempt sweep, not about the
janitor.

## Known growth / GC (future work)

The engine's retention story is still only the `jobs`-table item in
[`docs/design.md`](../design.md) (autovacuum tuning + delete old `succeeded`
rows). Checkpoint 9 adds two more sources of unbounded growth, recorded here
and in ADR 003's "Future work — garbage collection" so they are decisions, not
discoveries:

- **Install images** (`engine-deps:<install_key>`): one image per distinct
  requirements file × base digest. Never pruned today; a stale pin set leaves
  its derived image forever. Cache-busting is mechanical (`docker image rm`),
  but nothing schedules it.
- **Blobs and terminal workflows**: snapshot/patch blobs unreferenced by any
  `workspaces`/`workspace_patches` row, and workspaces belonging to a workflow
  that is `succeeded`/`failed`. The standing rule mirrors ADR 002: never
  delete anything a non-terminal workflow references; a terminal workflow is
  never retried, which is exactly what makes collecting it safe.

## docker-py 7.2 stream finding

docker-py 7.2.0's `logs()` demuxes/buffers client-side, so it cannot serve the
runner's live-streaming contract. The runner instead attaches its own raw
socket BEFORE the container starts and demultiplexes the docker stream frames
itself (`_demux` hardened against short/fragmented reads). Verified on a real
daemon: `OBSERVED stream separation: stdout='OUT-tail' stderr='ERR-line'`.
